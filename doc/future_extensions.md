# 未来可拓展功能设想

> 定位：记录设计/讨论中出现的**暂不实现**的扩展设想，避免遗忘与重复讨论。凡决定实现，必须先回写 `doc/top_design.md` 与 `doc/tasks.md` 正文，本文档不冻结任何契约。
>
> 现状基线（讨论立足点）：`top_design §9` 实验二模型 = core + `dbus_decode`（数据侧 MMIO 译码）+ `uart_ctrl` + `loader`（复位期写满 imem）+ `reset_sync`；哈佛（IMEM/DMEM 物理分离）；imem/dmem 默认各 1024 字 = 4KB。

每条设想统一给出：动机 / 对当前结构改动 / 成本 / 触发条件。实现前按 tasks.md §7 流程评估。

---

## 1. 取指侧 boot ROM 分区（固件 ROM + 用户 imem）—— 源自 loader 定位讨论

- **设想**：仿数据侧 `dbus_decode`，在取指侧加一个**指令侧地址译码**：低地址命中固件 ROM（只读、`.vh` 初值、永不被 loader 写），高地址命中 loader 可写的用户 imem。复位 PC 先进固件，由固件跳转到用户区。
- **动机**：把"固件"从可写的 imem 里**物理挪走**，loader/用户程序都不可能破坏固件；与真实 SoC 的 boot ROM + 程序存储同构。
- **改动**：小。
  - IF 侧仍是单读口、每周期只读一个地址，按 PC 范围组合选 ROM/imem → 纯组合，不碰流水级数/hazard_unit（同数据侧插 dbus_decode 同理）。
  - loader 写地址门控 `waddr ≥ 边界`，天然写不进 ROM。
  - core（§1–§8）不动；新增一个 IF 侧小译码模块（dbus_decode 的指令侧对偶）。
- **哈佛不变**：lw/sw 仍只走数据侧，永不到达取指侧任何存储。
- **触发条件**：实验二需"更正规的启动过程"，或固件需要防破坏/防自写。

## 2. 常驻 monitor 固件 + 软件上载运行（0x0–0x1000 固件区，0x1000+ 软件区）

- **设想**：imem 低区常驻固件，上电先跑固件；无软件时固件轮询等待；收到装载请求 → 触发 loader（CPU 复位）→ 软件写入 0x1000+ → 撤复位 → 固件见 `LOAD_DONE` → 跳 0x1000 执行软件；软件跑完按约定返回固件入口，继续轮询（可再装载）。
- **动机**：程序可在运行间隙轮换，无需每次重烧固件；结构类似小型 bootloader/monitor。
- **改动**：中。
  - loader 由"写满 imem"改为"只写软件区 0x1000+"（写地址门控）。
  - 新增 **固件 ↔ loader 控制寄存器**：`LOAD_REQ`（固件写 1 触发装载）、读 `BUSY/LOAD_DONE`——即 MMIO 加一个 soc 控制槽（§9.4 三个 uart 槽之外的扩展），loader 不执行指令，仅读该请求位启动。
  - **返回契约**：RV32I 中 `jal x0,0` 跳 PC+0（死循环）不是跳绝对地址 0；软件结尾须先 `lui+addi` 装目标寄存器再 `jalr`，或固件启动前把返回地址放入约定寄存器、软件 `jalr x0,0(xN)` 返回。
  - **固件再入幂等**：软件跳回后固件被多次"重进"，破坏性初始化（清内存、设栈）只能做一次，需区分首启/再入。
  - 软件 image 独立链接于 0x1000（`.org 0x1000`）；固件 `.vh` 与软件 `.hex` 分源。
- **与 §1 关系**：本模型固件仍躺在**可写** imem 低区（靠 loader 守边界）；§1 把固件挪到真 ROM 后更稳。可先用本模型、日后叠加 §1。
- **装载触发方式**（可并存）：固件轮询 UART 收命令才写 `LOAD_REQ`（"console 里敲命令换程序"，演示效果好，推荐主路径）；或板载按键直接让 loader 接管（固件被复位，载完再回固件）。
- **触发条件**：实验二要演示"换程序不重烧固件/多程序轮换"。

## 3. imem 扩容与分区参数

- 0x0–0x1000 = 4KB = 当前**整块** imem（`IMEM_WORDS=1024`）。若按 §2 让固件独占低区，需 `IMEM_WORDS ≥ 4096`（16KB，固件 4KB + 软件 ≥ 8–12KB），动 `top_design §6` 规模参数与综合面积/BRAM 策略。
- **触发条件**：采纳 §1/§2 前必做。

## 4. 数据侧 MMIO 从机扩充（timer / GPIO / 按键-LED / 数码管）

- `dbus_decode` 已具备 `cs_mmio/reg_off` 骨架与 rdata mux；加从机只需扩 reg_off/窗口位宽并接入 mux。作为实验二之后的接口外设练习或加分项。
- **触发条件**：实验要求扩展外设，或演示需要输入/灯/显示。

## 5. uart_ctrl 增强：波特率可配 / 收发 FIFO / 中断

- 现状：`uart_ctrl` 单 clk_en 分频、固件轮询 STAT（`top_design §9.4`）。若 console/monitor 要承载大量收发或演示效率，可加 FIFO（消抖轮询）或可配波特率。
- **触发条件**：串口吞吐成为瓶颈或演示需双向大数据量。

## 6. 中断/异常 + CSR（把"尾跳返回固件"升级为"被中断驱回固件"）

- 更通用的返回机制：软件被中断打断 → 进固件处理 → 返回。但 RISC-V 需 `mepc/mtvec/mcause…` 与特权语义，属架构级扩展，影响 isa、流水（需冲刷 + 关中断），成本高。
- **触发条件**：实验明确要求"可抢占/可中断"（当前无此要求，成本远高于收益）。

## 7. 双 bank / 乒乓 imem：边跑边写

- 当前约束"不得边跑边写"（§9.3）源于单 imem 取指与写口互斥。双 bank 交替：执行 bank A 时 loader 写 bank B，整 bank 切换后跳转——哈佛仍成立（lw/sw 仍不达取指侧），代价是 imem 面积翻倍。
- **触发条件**：需要"运行中后台预载下一程序、无缝切换"（当前演示用复位窗口即可，成本不值）。

## 8. 已讨论否决的方向（勿再提）

| 方向 | 否决原因 |
|---|---|
| 冯·诺依曼统一存储（lw/sw 可写指令存储） | 破坏"哈佛/非哈佛"判定依据；当前判定：运行期 lw/sw 到不了指令存储 → 保持**改良哈佛** |
| 把 loader 做成 CPU 上跑的固件程序 | 固件写 imem 须数据口能达指令存储 = 违反哈佛；且"CPU 复位期执行写 imem 的指令"本身矛盾（干活就要取指）。**loader = 独立硬件 FSM，不执行指令** |
